## 4. 各部分具体怎么写

### 4.1 需求分析

用 2–3 个连贯段落说明设备接入分散、设备使用权限和维护记录难统一的问题，再说明通过局域网主机整合 USB、蓝牙、Zigbee 设备的目标。不要以泛泛的“互联网飞速发展”代替项目实际问题。

功能需求按角色展开，并与用例 ID 对应。数据对象可以作为候选概念说明，但字段、权限粒度、工单状态、设备独占规则、异常阈值等未确认内容必须标为待明确。不得为了让报告“完整”而编造响应时间、并发量或运维成功率。

安全、完整性等描述应紧扣已知的权限校验和日志需求；具体技术措施写为设计方案，不能说成用例图已经规定。

### 4.2 用例模型

先列五个参与者，说明三个内部使用角色与两个外部交互参与者的区别，再放总体用例图。需要按角色拆图时，只能从总体图投影，不能另建一套功能定义。

必须说明：Admin 泛化到 Stu；UC2 包含权限校验、记录操作日志、登录认证；UC1、UC5 包含登录认证；EXT1 在监测到异常时扩展 UC9；EXT2 在运维人员请求 AI 辅助时扩展 UC11；G1/G2/G3 是 UC5 的三种接入特化。具体关系以 `AGENTS.md` 完整清单为准。

每个用例至少有可追溯的说明记录，使用下列字段。共享用例和特化用例可引用公共说明后仅补差异，避免重复复制。

| 字段 | 填写要求 |
| --- | --- |
| 用例 ID、名称 | 原样采用基准图，如 UC2 操作设备 |
| 参与者 | 区分发起者与外部交互者；不要将未关联角色写入 |
| 目标与触发 | 说明要完成什么、何时开始 |
| 前置条件 | 只写已有依据的条件；尚待设计的条件标注来源与状态 |
| 基本流程 | 按步骤列“谁执行什么、系统如何回应”，每步一个主要动作 |
| 备选/异常流程 | 标明发生在哪一步、触发条件、如何处理、回归哪步或如何结束 |
| 后置条件 | 成功或失败后产生什么结果，有无状态或记录变化 |
| 关联用例与扩展点 | include、extend、泛化及条件，与基准图一致 |
| 对应图号与待明确项 | 关联后续模型；没有图时明确说明，不伪造图号 |

### 4.3 静态模型

采用“候选对象来源 → 类职责 → 必要属性/操作 → 关系说明 → 类图”的写法。用户、设备、权限关联、操作日志、故障工单等可作为分析候选；当前并未确认其代码类、表结构或具体字段。

每条关系应解释业务含义及多重性的依据。角色泛化不自动等于代码继承；外部 AI 服务也不必成为数据库实体。不要照搬样例的 Person 公共父类或“一角色一类”。

图前说明模型范围，图后解释 2–3 个关键关系；不要只列 UML 术语而不解释本项目。

### 4.4 序列图与协作图（通信图）

沿用样例最清晰的写法：**场景目标 → 基本流程 → 备选流程 → 序列图 → 对应协作图 → 关键交互解释**。

- 同一组图必须使用同一场景、参与对象、消息含义和执行顺序。协作图的消息编号应能与序列图及文字步骤对应。
- 正文先说明业务，再使用界面、业务处理对象、设备交互对象等设计概念。对象名称和职责若尚未设计，标为候选，不能把样例的 WebInterface/DataManager 直接当作本项目架构。
- 异常既可在主图中清晰表达，也可在复杂时单独成图；不要为每个小分支机械复制整组图。课程若要求分别画图，则按要求分开。
- 查询无结果、权限拒绝、设备不可达、AI 调用失败等可作为后续设计时应分析的问题；具体恢复、重试、记录策略不得在未确认时宣称为既定需求。
- 图后说明分支条件及结果。调用 AI 不代表 AI 执行自动修复，自动建单也不代表自动触发运维。

### 4.5 活动图

用来解释一个业务过程如何推进、何处判断、由谁负责。文字按“开始条件 → 主要活动 → 判断分支 → 职责交接 → 结束结果”组织。

需要体现人员、系统、外部服务职责交接时使用泳道；单一流程不强制增加泳道。每个分支写明条件，避免只有菱形没有判断内容。分支后的返回点或结束结果应清楚。

优先分析操作设备、异常监测与建单、故障处理与按需 AI 辅助等有实际条件分支的场景。不得在活动图中绕过 UC2 的权限校验，或把 AI 辅助变成每张工单的必经步骤。

### 4.6 状态图

先说明“哪个对象的生命周期”，再列“当前状态—触发事件—条件—动作—目标状态”，最后绘图和解释。不以点击菜单、填写表单等步骤代替稳定状态。

设备与故障工单是可考虑的对象，但其状态集合、合法转换及关闭条件目前待明确。报告草稿可以记录候选设计；正式定稿前须明确依据，不得擅自固定为“待分配→处理中→已关闭”等既定流程。

### 4.7 构件图与部署图

分别回答两个问题：构件图说明系统由哪些职责单元组成及其依赖；部署图说明软件部署在哪些节点、通过什么通道与设备和服务通信。不要像样例末尾那样仅有构件图却称部署模型已完成。

本项目已知背景是软路由或局域网 Linux 主机与 USB/蓝牙/Zigbee 设备整合，AI Agent 是外部交互参与者。主机方案、数据库位置、网关拓扑及 AI 服务位置未确定，只能标为候选部署，不得凭空确定云厂商、端口或容器组件。

图前写职责或部署假设，图后解释主要依赖、通信边界和与用例的对应关系。构件粒度按实际职责确定，不要求一个类对应一个构件。

## 6. 图文组织与表达标准

### 6.1 每张图的最小说明单元

1. **图前引入**：说明对应哪个用例、何种场景、为什么需要此图。
2. **业务描述**：给出基本步骤，存在条件分支时说明触发条件及结果。
3. **模型图和题注**：名称包含场景与图型，使用明确的正文引用。
4. **图后解释**：指出关键关系、职责或分支，解释其对业务的意义，不重复朗读所有节点。

表达示例（已知需求层面）：

> UC11“处理故障工单”由运维人员参与。当运维人员请求 AI 辅助时，在“需要辅助诊断”扩展点触发 EXT2“AI智能故障分析”，并与外部 AI Agent 服务交互。后续交互图应分别表达请求辅助和未请求辅助的路径；具体输入、返回结果及失败处理仍需在设计阶段明确。

这类段落直接解释本项目，不应被“序列图是一种描述对象交互的图”之类的定义段落取代。模型类型的定义最多简要交代一次。

### 6.2 命名和图号

- 所有标题使用正式项目名；使用原始用例图时说明旧标题差异，正式报告中的展示图标题应统一，保留源图追溯。
- 用例名称沿用图中文字。不要把“查看设备状态”和“监测设备状态”合并，也不要混淆“管理工单”和“处理工单”。
- 序列图与协作图（通信图）术语首次说明后保持统一，不能将两者当成不同业务需求。
- 默认图号按章连续编号，如“图2-1 系统总体用例图”；表号独立编号。若采用单章形式，可沿用“图1-n”，但不得混用体系。
- 图下方居中放题注；表标题放表上方。同组图题注必须各自唯一，不使用无场景限定的“备选过程A”作为唯一名称。
- 使用自动题注和交叉引用；图增删后更新域，并检查实际显示值。

### 6.3 排版默认值

以下是没有学校指定格式时的项目建议，不是对样例全部样式的机械复刻。

| 项目 | 建议 |
| --- | --- |
| 纸张与页边距 | A4 纵向；可参照样例上/下 2.54 cm、左/右 3.175 cm，宽图必要时使用独立横向页 |
| 正文 | 宋体 12 pt，1.5 倍行距，普通正文首行缩进 2 字符；不对标题、题注及表格机械套用首行缩进 |
| 标题 | 使用 Heading 样式，一级黑体 18 pt，二级 14 pt，三级 12 pt 加粗；编号与真实层级一致 |
| 图内文字及题注 | 以最终纸张大小可读为准，建议不小于 10.5 pt；图过密时拆分，避免只缩小整图 |
| 图示风格 | 同一套颜色、字体及箭头样式；优先清晰矢量图或高分辨率导出，不照搬 Rose 界面截图 |
| 目录与页码 | 自动目录；封面可不显示页码，正文连续编号；检查分节后编号是否重置 |
| 分页 | 标题与后文保持相邻，图与题注尽量同页；使用段落属性和分页设置，不以大量空段落撑版 |

学校明确要求优先于这些默认值。文档中的任何模板字段都必须在最终交付前填妥或明确说明缺失，不复制样例作者资料填充。

## 7. 写作流程与交付检查

建议按“用例追溯表 → 用例文字说明 → 静态对象候选 → 关键场景图 → 状态/构件/部署模型 → 图文核对 → 排版”推进，先解决内容对应关系，再整理版式。

- [ ] 正式项目名一致；没有遗留学籍系统、原作者或旧工具的无关内容。
- [ ] 五个参与者、19 个用例均覆盖，角色职责及全部关系与基准图一致。
- [ ] AI 分析保留为按运维请求触发的扩展，不变成强制步骤或自动修复。
- [ ] 文字步骤、交互消息、活动分支、对象状态及构件职责相互对应。
- [ ] 没有把候选字段、工单状态、权限粒度或部署方案写成已确认需求。
- [ ] 每张图都有明确用途、题注、正文引用和必要解释；同组序列图/协作图一致。
- [ ] 图号唯一且连续，引用正确，目录和页码已更新，没有分节误重置。
- [ ] 状态图有明确对象；构件图与部署图分别交代；未完成项如实标注。
- [ ] 逐页渲染检查图中文字、箭头、跨页、表格和题注；结构校验不能替代视觉检查。
- [ ] 总结只评价实际完成的建模工作，不虚构开发完成、测试结果或硬件验证。

本标准当前交付为 Markdown，便于版本管理和持续修订。后续生成 Word 报告时再执行文档结构、域更新及逐页视觉验收。
